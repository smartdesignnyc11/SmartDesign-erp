## What it does
- **Sign-in and roles.** Supabase email sign-in, and Sign In with Google (on since 2026-10-19; the button shows only while Supabase's Google provider is on). Google never creates an account: sign-up is off, so only invited addresses get in. A new account is role `none` and sees nothing. Only the owner sets a role (`public.profiles`); sign-up metadata is ignored.
- **One truth, many phones.** `public/cloud.js` stores the app's DB as one row per collection and per job. Every save names the version it was based on; a stale save is refused, merged record by record (`merge3`) and saved again. Edits a phone could not sync are pushed at the next boot before the server copy is pulled. Changes arrive by the Supabase change feed, with a 30-second version poll behind it.
- **Security in the database.** Office roles (owner, PM, coordinator, designer, design director, billing, controller) see everything in their workspace. Field roles (foreman, crew, driver) never receive the books, bank, payroll, bills, deals or investors, get money keys stripped from jobs, cannot write the company records, and their saves get the stripped money put back by the server. Clients and the M&B roles are refused until per-client rows exist.
- **AI.** `/api/ai` (netlify/functions/ai.mjs) streams: it reads Anthropic's event stream, keeps the connection alive with spaces (Netlify cuts an idle response at 30 s), and sends the whole message as JSON at the end, so the app reads it unchanged. At 52 s (Netlify stops functions at 60) it sends what has come, marked `time_limit`, and charges the time at the model's top speed so thinking tokens cannot slip past the caps. Measured: a 4,000-token answer in 41 s; an 8,000-token brain answer cut at 54 s and logged. It needs a signed-in member, picks the model by tier, drops page-only fields (MCP servers, sampling, thinking budgets), checks this month's spend against the person's and the firm's cap before calling, and logs who, model, tokens and cost to `ai_usage` (never the prompt or the answer).
- **Private to each person.** What came from a person's own Google account (mail, Google Calendar entries, Drive files), their Google connection and their assistant live in `own:<sign-in id>:<collection>` rows. The database lets only that sign-in read or write them, the owner included; `cloud.js` splits them out on save and rejoins them on load, and a device only ever sends its own person's. Job chat, logged calls and ERP calendar holds stay shared.
- **Device settings stay on the device.** Who is using it, their role and name, the job on screen, notifications and the mail marker are never synced (early builds did, and one phone's save switched every other device to that person); the server refuses them.
- **Google connection.** The firm's client ID is in the app's settings; each person connects their own account under Connections, and mail, calendar and Drive are checked while the app is open.
- **One person, several sign-ins.** `profiles.private_key` links sign-ins of one person to one private store (Alan's two addresses). Only the server sets it; nobody signed in can change it.
- **The watcher.** Settings › Connections › Keep Watching When It Is Closed hands the server a one-time Google code; `google-connect` trades it for the long-lived key, seals it (AES-256-GCM, `WATCH_KEY`) into `google_watch`, which nothing signed in can read. `assistant-watch` runs every 15 minutes, weekdays 7am to 7pm New York: each person's new mail, calendar changes and Drive files go into their private `own:<key>:inbox` row; the app files the inbox on opening through the same code as a browser sync (`gsIngestServer`), then empties it. While watching, the browser takes its short-lived Google key from the server, so opening the app syncs with no Google window. The watcher only reads; it cannot send mail or change a calendar. Disconnect revokes the key at Google and deletes it.
- **The watcher's key reads only** (Gmail, Calendar and Drive read-only, `include_granted_scopes` off); `google-connect` refuses and does not keep any key that could send, change or delete. Sending, drafting and booking from the app ask Google in its own window at that moment (`gcFetch` falls back on an insufficient-scope answer), so a stolen server key could read but never send mail as anyone.
- **Push notifications.** Turning on Settings › notifications registers the device (`push_subs`, filed under the private key, unreadable by anyone signed in) and sends a test. After each run the watcher scores what it found (`lib/score.mjs`: a vendor or client on file or their company domain, a job's name or address, a city agency, a calendar entry in the next 48 hours; never promotions, social, newsletters or one's own sent mail) and sends at most one notification naming the first three. Web push with VAPID keys (public in config.js, private a Netlify secret). On an iPhone the app must be added to the Home Screen first.
- **New messages buzz the phone (`/api/notify`).** After a new line saves, the app asks the server to tell the people it is for: the other members of a direct or group thread, or the people a job-thread line @mentions. The server reads the conversation itself: the caller must be able to read it and be the line's sender; a field person is told only on a job they are on, never of a client-thread line or a line with a money card; never the sender; at most one per conversation per person every 2 minutes (`notify_sent`, `notify_claim`). Tapping it opens that conversation. With no signal the ask waits and goes when the phone is back.
- **The watcher's finds reach the assistant.** Filing the inbox runs the same follow-up as a browser sync: `paWatch` turns what matters into nudges in the person's assistant conversation (once each), today's brief is rebuilt, the lessons loop runs.
- **Team tools (`/api/team`).** The owner invites people from Settings › Team Accounts (email, role, person in the app; Supabase sends the email; nobody can be invited as a second owner; an address already here just gets the role). Sign Out Everywhere (the owner for anyone, anyone for themselves) deletes the account's sessions and its notification registrations.
- **A session the server ended is dead at once.** Every database check requires a live session (`session_alive()` inside `my_role()`), and the functions check it too, so a lost phone's unexpired key reads and writes nothing from the moment it is signed out. The phone notices within 30 seconds (or at its next start), deletes its local database (records and photos) and its stored sign-in, and shows the sign-in screen.
- **The document reader (`/api/doctext`, the lost doctext.mjs rebuilt).** The app sends a file and gets its text: PDFs with a text layer and Word documents are read on the server at no cost (unpdf, mammoth); scanned PDFs and photos (receipts, slips, certificates) are read by the small Claude model through the same capped, logged door as every AI call (`claude()` in ai.mjs, logged as `small:doctext`); spreadsheets (.xlsx) are read sheet by sheet by a small built-in reader (values only, no formulas or macros run, limits against hostile files, no third-party package); old .xls, iPhone HEIC photos and files over 4.5 MB get a plain note of what to do. Files are read in memory and not kept.
- **The books' seals, held by the server (`/api/seal`, `period_seals`).** When the owner or the controller closes a month, the app uploads the books and the server recomputes that month's chain from its own copy: SHA-256 (its seal) and the app's FNV-1a head (to show whether the closing browser saw the same books). Seals are add-only; nobody signed in can change or delete one, the owner included. Verify the Books adds a "Held by the Server" section: the server recomputes from its books now and names any posting changed, missing or added since its seal. So a month rewritten in a browser copy, seal included, is still caught.
- **The shell opens from the phone's copy.** The service worker serves the stored page at once and refreshes it from the network for the next open (a new build shows one open late); data and `/api` are never cached.
- **Streaming to the page.** `body.stream: 'client'` makes `/api/ai` pass Anthropic's event stream straight to the page (first words in about 2 s), then one `event: sd_done` with the usage and whether it was cut at 52 s; the cost is logged as usual. Without it the door returns one JSON message.
- **The nightly Brain** (`brain-nightly` at 07:07 UTC, `brain-background` up to 15 minutes, `/api/brain` for the owner to run it now). It reads a digest of the firm's records (`lib/digest.mjs`: late schedule, decisions and materials, open COs, overdue tasks by owner, obligations due, late POs, held bills, open meeting steps, what is already learned or proposed), never private rows (mail, calendar, Drive), with the live Standard as its instructions, and proposes at most five changes with reasons, the Standard value and the records as evidence, into the owner's private inbox. The app files them as drafted changes in Company › Changes (`bnIngestServer`); approving queues one for the next build; nothing changes a setting or a record on its own. One top-model call a night, charged to the owner within the caps.
- **The field receives only its jobs.** A job's crew is the job's own list (`p.team`), set by the PM or the owner (Messages, the job's team thread, Change Crew; or Project Settings). A field sign-in reads and writes only the jobs whose crew names its person (`field_job` in the view, the save and the change feed); a job with no crew is the office's alone; a field save never changes a crew. A phone drops a job it was taken off at the next version check, change event or refused save. On first open an office device gives each job its first crew from the last 60 days' time, daily logs, requests and thread lines. Not yet scoped per job: the shared collections a field phone reads (orders, photos, daily logs, time, tasks) still hold every job's records.
- **Message threads are private to their members.** Each direct or group thread is its own row (`thread:<id>`); the database shows and accepts it only for members (by the person in the app, `profiles.app_user_id`, which the owner sets), the owner included, and nobody can join a thread by adding themselves or write one for others. A device sends only its person's threads. Where each person stopped reading each conversation is theirs alone (`DB.msgSeen[uid]`, a private `own:` row like the assistant), so reading never rewrites a shared job or thread and nobody sees when a colleague read what; the markers phase 1 kept in the shared rows move there once per person.
- **The assistant's rules travel on the firm's log.** Each person's assistant is a private row, so a rule the owner sets for someone (Act Alone, Ask First, Hand It to Me) is kept on the firm's delegation log; that person's device applies it when it is newer than their own last choice, and the owner's screen reads it back from the log (`paPolicyApply`, `paRule`). Later choice wins, as on one device.
- **Two devices make the same automatic records.** Recurring duties take their key as their id, so two phones opening the same morning make one Friday update, not two. Demo seeders never run once the server holds the firm's records; `tests/seed_guard_test.py` fails on any seeder that is not on that guard.
- **Partial records do not stop the app.** A job or message from the server missing its lists is repaired on arrival (`normalizeProject` in cloudApply, `cmInit`), and boot tolerates a job without tasks.
- **Seeding.** Once the server holds the firm's records, no device seeds demo data (`window.__sdServerTruth` in `sdSeedsOff`). The first office sign-in on an empty workspace uploads that device's records.

## Build, deploy, test
```
cd platform
python3 build.py                     # builds ../dist, then public/ (index.html, config.js, sw.js, vendor/)
mkdir -p .netlify && echo '{"siteId":"1bdb5200-477c-492a-8294-fb475014deaa"}' > .netlify/state.json   # links the site (the CLI's --site flag fails here)
NETLIFY_AUTH_TOKEN=x netlify deploy --prod --dir public --functions netlify/functions   # the session proxy supplies the real token
npm test                             # merge, AI proxy, private records, watcher, notification-rule, document-reader, books-seal, field-jobs and message-notification unit tests (offline)
SDP_APP_HTML=/abs/app.html python3 build.py   # deploy an app build made elsewhere, so dist/ is not rewritten under a running net
python3 test/ingest_test.py          # the app files the watcher's inbox like a sync run (local build)
python3 test/qa_accounts.py /abs/qa_users.json      # QA accounts (qa workspace), passwords written outside the repo
SD_QA_USERS=/abs/qa_users.json python3 test/live_db_test.py    # the database rules as each role, live (QA workspace)
SD_QA_USERS=/abs/qa_users.json python3 test/live_fieldjobs_test.py   # the field receives only its jobs, live (QA workspace)
SDP_PG='-h /var/run/postgresql -U postgres' python3 test/schema_pg_test.py   # schema.sql's rules on a local Postgres, offline
SD_QA_USERS=/abs/qa_users.json python3 test/live_app_test.py   # owner on desktop + foreman on phone, live
SD_QA_USERS=/abs/qa_users.json python3 test/live_speed.py      # a mid-range phone opening and reopening the hosted app
```
The QA accounts file lives outside the repo. The live tests only touch the `qa` workspace and empty it first.
`supabase/schema.sql` is idempotent; apply it with the management API (`POST /v1/projects/<ref>/database/query`).

## Not built yet
per-client rows for the portal (clients stay refused), Plaid, the agents beyond the nightly Brain (BACKLOG §5 items 3–8), HEIC photos in the reader. Field roles receive only their jobs' rows, but the shared collections (orders, photos, daily logs, time, tasks) are not yet filtered per job. A field phone's writes to collections it may only read (company, clients, users, vendors, obligations) are not sent and are replaced at the next pull; anything a field role does must land in a collection it may write (jobs, tasks, its own rows, its threads).
